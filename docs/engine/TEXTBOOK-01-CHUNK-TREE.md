# Engine textbook, chapter 1 — the chunk tree

> Files: `src/Engine.Core/Chunk.fs`, `ChunkTree.fs`. Tests:
> `ChunkTreeTests.fs`, `ChunkTreePropertyTests.fs`. Decision:
> ADR 0011 E2/E3; spec §5 (the locked data model).

## What a chunk is

The atomic unit of everything the engine holds: one typed node
of content. `ChunkKind` is the closed vocabulary — markdown
block kinds (heading with level, paragraph, list + item, code
with optional language, quote, thematic break) plus the
interaction kinds (user request, tool use with name, tool
result with error flag, agent error, system note). The kind is
load-bearing: narration, export, spatial pitch, and wire format
all dispatch on it, so adding a kind is a compiler-guided tour
of every consumer (development guide §2).

A chunk carries **three identities**:

- `Id: ChunkId` — a GUID, allocated at append, never reused,
  never positional. Everything that points at content (the
  navigator's focus, notebook pins, branch anchors, the
  session file) points by id, which is why reordering and
  branching can never invalidate anything.
- `CaptureSeq` — its place in *time*: a session-global,
  strictly increasing integer. The capture order IS the
  transcript (spec §5.3's immutable record).
- `AuthoredIndex` — its place in *structure*: position among
  its parent's children. Present from the first commit so the
  editor layer never needs a model migration (ADR 0011 E3).

`Parent: ChunkId option` makes the forest: `None` is the main
thread's top level; a clarification branch is just a
`UserRequest` whose parent is the chunk it asks about (spec
§5.1 — "a child branch anchored to the chunk it is about").

## The tree and its API

`ChunkTree.Tree` is an immutable value: a map of chunks by id,
a children index keyed by `ChunkId option`, and the next
capture sequence. The representation is `private` — the only
constructors are `empty`, `append`, and `restore` (chapter 9),
so no caller can ever build an inconsistent tree.

Every read is **total**: `tryFind`, `children`, `parent`,
`nextSibling`, `prevSibling`, `firstChild`, `inCaptureOrder`
return options/lists, never throw. This is a navigation
requirement disguised as API design: a blind user probing the
edges of a structure does it *by pressing keys*, and a probe
must always be answerable.

`append` is the single write. It validates the parent exists
(a typed `Error` otherwise), assigns id + both orderings, and
returns the stored chunk with the new tree. Cost honesty: the
children list append is O(siblings); fine at conversation
scale, and a future O(1) variant hides entirely behind the
private representation.

## The laws and their tests

Example-based tests pin behaviour; FsCheck properties pin the
laws over **every reachable tree** (a generated byte list
scripts each append's parent choice):

- count = number of appends; capture order = insertion order.
- every chunk sits in its parent's child list exactly at its
  authored index; every listed child points back.
- `nextSibling`/`prevSibling` are inverse where defined;
  `firstChild` agrees with `children`.
- a branch under an anchor leaves the main thread's shape
  untouched (the §8.1 no-drift invariant at the model layer).

## Why not a mutable tree, or a list?

The spec's anti-reference (§3) is the flat append-only chat
log — the data model that *causes* the lost-context phenomena
the engine exists to fix. The tree gives anchored branching;
immutability gives free snapshots (the host hands the tree to
narration mid-update without locks beyond its own), honest
time-travel (the session file is just `inCaptureOrder`), and
the two-orderings trick gives the future editor (reorder
changes authored order; capture order never lies about
history).
